# 共域 CoField · 产品语言与界面原则

- 面向：把严谨的领域模型翻译成一个正常人愿意用的产品
- 适用范围：所有用户可见文案、界面结构、通知、错误提示
- 与其他文档的关系：领域词汇见 [`CONTEXT.md`](../CONTEXT.md)，产品机制见 [`02-产品设计`](./02-产品设计.md)

---

## 1. 这份文档存在的原因

这个项目最大的落地风险不是技术，是**严谨性泄漏到界面上**。

后端有同意凭证、记忆切面、成局证明、稳定性检查、匹配信封、代理授权。这些概念都必须存在，否则产品的承诺是假的。但如果它们原样出现在屏幕上：

> "请确认您本次匹配信封的字段授权范围与有效期"

一个大二学生会立刻关掉。

**核心判断：后端严谨 ≠ 前端严谨。**

严谨性应该被**感受到**，不应该被**阅读到**。用户应该觉得"这个产品不糊弄我"，但不应该读到任何一个治理术语。

## 2. 语言映射表

左边是领域词汇（代码、文档、数据库里用），右边是用户词汇（界面上用）。**两侧不得混用。**

| 领域词汇 | 界面上的说法 |
|---|---|
| 意图信号 | "你想做点什么？" |
| 意图编译 | （不出现，表现为系统帮你整理好的一张卡） |
| 匹配信封 | "这次让他们看到我的" |
| 代理授权 | （不出现，授权就是那个勾选动作本身） |
| 同意凭证 | （不出现，就是那个确认按钮） |
| 成局提案 | "一个小队" / "这几个人" |
| 成局证明 | "为什么是这几个人" |
| 稳定性检查 | （不出现过程，只出现结论）"他们现在都没有更想去的组" |
| 条件响应 | "我可以，但……" |
| 行动承诺 | "我加入" |
| 撮合窗口 | "明早 8 点开始配队" |
| 硬约束 | "必须满足的" |
| 软目标 | "会尽量考虑的" |
| 阻塞证明 | "这个组暂时凑不出来，因为……" |
| 共同事件 | 直接用项目自己的名字 |
| 共域 | "我们的空间"，或直接就是项目名 |
| 场域智能体 | 给它起个短名字，或者干脆只是一张会说话的卡片 |
| 意图使者 / 个人代理 | **完全不出现** |
| 共同素材 | "我们做的东西" |
| 行动回声 | "这次留下了什么" |
| 记忆切面 | "我的经历" |
| 共同行动边 | （不出现） |
| 持续共同体 | "我们这个小组" |
| 曝光公平 / policy_epoch / TTL | （不出现） |

### 2.1 这条规则可以被机器检查

CI 里加一条：**用户可见文案中不得出现领域词汇黑名单**。

黑名单直接从 [`CONTEXT.md`](../CONTEXT.md) 的术语表生成。检查**只针对面向学生的可见文案**（i18n 资源、组件字面量），三类表面不在范围内：

1. **申诉、数据导出、争议处理**——这些场景必须展示完整领域信息（见 §7）
2. **运营与安全后台**——运营人员是领域词汇的合法使用者
3. **内部文档、PRD、代码注释、工程师视角的用户故事**——本来就该用精确词汇

术语泄漏是可测的，不应该靠 review 时凭感觉抓；但检查范围搞错了会制造噪音，把工程师说"稳定性检查"也报成错误。

## 3. 四条界面原则

### 原则一：严谨性要能被感受到，不能被阅读到

成局证明是最好的例子。它的可信度来自**具体**，不来自术语：

```
❌  该提案已通过多目标约束求解与稳定性校验
✅  周三晚上你们三个都有空，陈牧之前剪过两支短片
```

后者没有一个专业词，但比前者更让人相信。

### 原则二：每屏一个决定

产品每一屏只问用户一件事。授权、接受提案、确认回声——三件事三屏，不能合并成一个"设置页"。

用户在一屏里被问两个问题时，会两个都不认真答。

### 原则三：权利必须顺手，不能庄严

撤销一条记忆应该像删一条朋友圈那么简单，不应该像提交一份数据删除申请。

```
❌  [ 发起数据主体权利请求 ]
✅  [ 撤销 ]
```

**如果行使权利需要仪式感，用户就不会行使。** 而一个没人行使的权利等于不存在——这会让 04 那份权利矩阵变成一纸空文。

### 原则四：AI 可以很能干，但不能让人依恋它

这条容易被写成"AI 要少做事"，那是错的。**帮忙聊和被依恋是两件事。**

区别在于 AI 服务的是"这段关系往前走"还是"用户和 AI 待在一起"。前者做完就退场，后者要求用户回来找它。

**可以做，而且应该做得好：**

- 帮你起草、帮你破冰、帮你把话说清楚
- 你忙的时候替你先接住话头（模式与披露策略见 §4.1）
- 在空间里协调、提醒、整理证据

**应当避免：**

- 模拟自己的生活、24 小时更新状态、主动惦记用户
- 发展出可供依恋的人格
- 抢占主界面

界面上的四条硬要求：

- 场域智能体是角落里的卡片，不是中央的对话框
- 说话短，一次不超过两句
- 绝不主动弹窗
- 每条建议都带一个"不用了"

> **反面证据**：Tara 的副标题是"帮你聊 帮你找"，但用户评价里被反复称赞的是塔罗准、"被治愈了"、"有人陪真的太好了"——**没有一条在说它帮自己找到了人**。陪伴会吃掉连接。详见 [`05-研究依据与评审`](./05-研究依据与评审.md) §6.2。

## 4. 代聊模式的用户表达

三档模式，用户自己选，可按会话切换：

| 用户看到的选项 | 实际行为 |
|---|---|
| **我自己说** | 默认 |
| **帮我想怎么说** | AI 起草，你过目后发出——发出的是你 |
| **先帮我接着** | AI 代答，直到你回来接手 |

第三档是否让对方知道，由 `agent_reply_policy` 决定（行动类别注册表字段，可按校园与场景配置），不写死在产品里。

如果选择披露，做法是**常态化轻标识**：消息旁一个极轻的标记，不弹窗不打断。关键在于它是常态——**当所有人都知道 AI 可以帮忙接话，用 AI 就不再是丢人的事**，也就不存在"被发现"那一刻。

文案上不要把它做成一个功能开关的样子：

```
❌  [ ] 启用 AI 自动回复代理
✅  你先忙，我帮你接着？        [ 好 ] [ 我自己来 ]
```

**无论哪一档，AI 都不能产生承诺。** 涉及是否加入、是否见面、是否披露更多身份时，必须切回真人——这一条不可配置。

## 5. 七个面的用户视角命名

| 内部叫法 | 界面上叫 | 用户在这里做什么 |
|---|---|---|
| 意图面 | **想做点什么** | 说一句话，确认系统整理得对不对 |
| 提案面 | **给你找的人** | 看两个小队，选一个或都不选 |
| 共域面 | 项目自己的名字 | 推进这件事 |
| 回声面 | **这次留下了什么** | 逐条决定留不留 |
| 我的事件 | **我参加过的** | 看自己做过什么 |
| 我的记忆 | **关于我的记录** | 看系统记住了什么，改或删 |
| 我的授权 | **谁能看到我** | 收回不想给的 |

## 6. 具体改写对照

这几条是最容易写错的地方，直接给出正误对照。

**授权页**

```
❌  请确认您本次匹配信封的字段授权范围与有效期
✅  这次让他们看到什么？
    （下面是勾选项，右上角小字：72 小时后自动失效）
```

**稳定性结论**

```
❌  该成局提案已通过稳定性检查（Nash 近似）
✅  这几个人现在都没有更想去的组
```

**记忆争议状态**

```
❌  记忆切面 mf_8f3a 已进入 contested 状态
✅  苏晚对这条有不同意见，先不用了
```

**多方审批进度**

```
❌  行动回声草稿待多主体审批（1/3）
✅  还差陈牧和苏晚点头
```

**无可行解**

```
❌  当前市场单元流动性不足，建议放宽非安全硬约束
✅  这周东校区会剪辑的人不多。
    要不要把截止改到下周？这样能多出 14 个人
```

**不确定性提示**

```
❌  该候选缺乏夜景场景的已验证经历证据
✅  苏晚没拍过夜景，这块还没底
```

**AI 草稿标识**

```
❌  [approval_state: draft] 系统推断
✅  这是我猜的，你看对不对
```

## 7. 什么时候必须显示完整领域信息

三个场景例外，此时**必须**展示完整的来源、时间戳、审批链和术语原文：

1. **申诉** —— 用户质疑某个判定时，要能看到完整依据
2. **数据导出** —— 导出格式按 ISO/IEC TS 27560 结构，不做简化
3. **争议处理** —— 涉及多人冲突时，运营和当事人看到的是同一份完整记录

做法：日常界面用用户语言，每个对象提供一个不显眼的「详细信息」入口通往完整视图。

**日常简化，追责时完整。** 两者不冲突，但不能反过来。

## 8. 语气

面向大学生，但不装年轻。

- 用短句。一句话说一件事
- 不用感叹号堆热情
- 不叫用户"小伙伴""同学们"
- 不给功能起花名（"心动匹配""缘分小屋"）
- 拒绝和失败要平静：不安慰，也不冷冰冰，直接说下一步能做什么
- 涉及权利的地方要肯定：说"你可以随时撤销"，不说"您有权申请撤销"

## 9. 一个待决问题：产品对外叫什么

"共域 / CoField" 是一个**内部代号**。它准确，但对学生来说偏抽象——没人会跟同学说"我在共域上找到队友的"。

对外名字应该：

- 能被口语化地说出来（"我在 XX 上发了个组队"）
- 指向"一起做事"而不是"交友"
- 不撞校园墙、组队软件的既有联想

**副标题比名字更要紧。** Tara 的"帮你聊 帮你找"是好范本——两个动词四个字，一句话说清产品干什么。我们的副标题也该是动宾结构，候选方向：

```
找到人，把事做成
帮你找人，帮你成事
```

判断标准只有一条：**一个大二学生看完这五六个字，能不能立刻说出这产品是干嘛的。**

**名字和副标题都应该做用户测试，不应该由团队投票决定。** 在测出来之前，代码和文档继续用共域，界面上留占位。

界面呈现的具体规格见 [`08-前端规格`](./08-前端规格.md)。
