# ADR 0013 · 投递范围与逐项授权是两个轴

- 状态：已采纳
- 日期：2026-08-12
- 相关：不变量 7、ADR 0010、issue #25（这条 issue 标着 `needs-triage`，
  等的就是这个判断）
- 触发：issue #25 问「投递范围和 `match_envelopes` 的逐项授权在概念上重叠，
  是两件事还是一件事的两面？」

## 背景

两者都影响"别人能看到什么"：

- `match_envelopes`：这次露出我的哪几项（手机号给不给看）
- `intent_signals.reach`：这条需求问谁（全校 / 只问一起做过事的人）

想不清楚就做，很可能得到两套互相打架的可见性规则——**而可见性规则一旦互相
打架，用户就再也搞不清自己的东西谁能看到**。

## 决定

**两个轴，不是一件事的两面。**

| | 授权（`match_envelopes`） | 范围（`reach`） |
|---|---|---|
| 管的是 | 这次**露出什么** | 给**谁**看见 |
| 后悔的形状 | "我不想让全校看到我的手机号" | "我只想问熟人" |
| 粒度 | 逐项 | 整条需求 |

两者**相乘**就是最终可见性，没有互相覆盖的规则：
范围决定这条需求进不进某个人的候选池，授权决定进了之后他看见其中的哪几项。

分开问，因为它们分别会被后悔。

## 「熟人」由什么定义

**共同完成过的事**，不是好友列表，也不是平台觉得你们熟——
不变量 7 说关系图谱是共同事件的可重建投影，不是主观判定。

实现在 `matching/funnel.py` 的硬过滤里：查 `event_members` 中与我同事件、
且双方都没退出的人。

### 第一次用的人在这一档下得到零个候选

**那不是 bug，是这一档的真实含义。**

所以发布页在**他选之前**就说出来：
「你还没和谁一起做成过事——选它现在会一个人都问不到」。

让他选完、等一轮、再看见一屏"没找到"，他会以为是这产品没人用。
走查第⑪幕守着这句话。

## 「指定范围」不做

按组织、按院系、按具体的人——它要一套选择器，而在还没有人抱怨"问的人太多"
之前，那套选择器只是一个必须被填的表单。

留成两档：全校（默认）/ 只问一起做过事的人。

**默认必须是全校**：冷启动时缩小范围等于没有匹配。

## 契约上的两处

- 两个不同的概念不能同名。条目的「谁能看见」（`ours`/`outside`）原来也叫
  `Reach`，在 OpenAPI 里只活下来一个，前端拿到的是另一个概念的取值。
  条目那个改名 `ItemReach`。
  **「一个概念在 DB / API / 前端同名」反过来说，就是两个概念不能同名。**
- 请求那一侧 `reach` 故意留成 `str`（认不出的值退回全校），响应那一侧是枚举。
  **宽进严出**：前端取值仍然从契约派生，而一个打错字的参数不该让整条请求 422。
