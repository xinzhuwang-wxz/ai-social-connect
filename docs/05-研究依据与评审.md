## 1. 理论依据：五个判断，五份出处

| 产品判断 | 理论依据 | 出处 |
|---|---|---|
| 人是事件的投影，人-人关系不存储而是算出来的 | **人与群体的二重性**：人-人网络与群-群网络都是同一个"人-群"二部图的投影，二者互为对偶 | Breiger (1974)；[双投影方法, PLOS ONE](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0097823) |

### 1.1 为什么"人是事件的投影"值得单独说

Breiger 的二重性原理被称为"人文社会科学少数几个真正的突破之一"。它的含义是：**人-人社交网络从来不是原始数据，而是"人参加了哪些群体/活动"这张二部图的一个投影。**

这直接决定了存储结构：存超边（事件 + 参与者），人-人关系按需投影出来。反过来存"好友度"字段，等于存一个投影的离散化快照，会立刻与事实脱节。

### 1.2 超图为什么是 N+1 的数学根据

抖音小火人把关系建模成一条 pairwise 边，精灵挂在边上。结果是：5 个朋友必须养 5 只，且不支持 3+1。产品负责人在问答中自陈这里"有点 tricky"——tricky 的根源是数据结构，不是产品设计。

**从 pairwise graph 升级到 hypergraph，就是 2+1 → N+1 的数学表达。** 这是本产品最强的结构性差异化论据，且它有文献支撑而不是主观选择。

### 1.3 稳定性：一个容易被优化思维掩盖的机制漏洞

组队是 hedonic coalition formation game。关键结论：**求解器算出的最优分区未必是稳定分区。**

在一个人人可随时退出的自愿产品里，不稳定的分组会自己散架。CP-SAT 的全局最优解可能包含一个"为让整体目标最大化而被塞进不喜欢的组"的成员——他会在第一次线下见面前退出，整组随之崩掉。

这就是为什么 [`03-技术架构`](./03-技术架构.md) §8.6 在求解之后强制加了一道稳定性检查。

### 1.4 撮合时机不是产品口味问题

Akbarpour–Li–Oveis Gharan 的结论有一个明确前提：**平台能否识别参与者何时离开市场**。

- 能识别 → 等待增厚市场收益很高，且比提速更重要，在有等待成本时依然稳健
- 不能识别 → 贪心即时撮合已接近最优

我们的意图**自带 deadline**——用户主动告诉了我们退出时间。所以我们处在"能识别"的情形，窗口清算是有依据的默认选择，而不是流动性不足时的补救。

论文也讨论了随之而来的**激励问题**：用户有动机谎报紧急程度。这个问题必须正视，不能假装 deadline 是诚实上报的。

## 5. 评审记录：被推翻的判断

诚实记录哪些结论变过。**包括我们自己先提出、后又收回的建议。**

### R1 · 收回：推荐 Graphiti 作为记忆层

- **原判断**（本项目早期架构调研）：采用 Graphiti，理由是 episode 溯源 + bi-temporal + group_id 多租户。
- **推翻理由**：
  1. bi-temporal 这一条已被 **PostgreSQL 18 原生时序约束**覆盖，system time 用一个 `record_time` 字段即可；
  2. Graphiti 强制引入 Neo4j / FalkorDB / Neptune，打破"Postgres 是唯一权威"；
  3. **最根本的一条**：Graphiti 的核心能力是"LLM 从非结构化文本自动抽取实体与关系"，而这恰是本系统**明确不要**的能力——我们的事实来自结构化行动证据（谁确认了、谁上传了、谁完成了），不是 LLM 从聊天记录里推断的。用一个以自动抽取为卖点的框架，承载一个"禁止未经确认的 AI 推断成为事实"的系统，是方向性错配。
- **保留的借鉴**：episode 概念（每条派生事实可追溯到一条原始记录）与"失效而非删除"，直接实现在自有表里。

### R2 · 推翻：以"48 小时来不及"为由否决基础设施

- **原判断**：早期设计以竞赛交付为前提，把 Letta、Graphiti、图数据库、独立向量库统一以"48 小时来不及 / 双数据源运维成本"否决。
- **推翻理由**：产品已明确按完整、可扩展系统设计，交付时间不再是约束。**这些否决理由全部失效，必须以技术理由重新评估。**
- **重新评估结果**：Graphiti 仍排除（见 R1，但换成了技术理由）；独立图库仍排除（换成"查询浅层 + AGE 可在同库内满足"）；Letta 从"明确不选择"降级为"可选，有明确门槛"（见 R3）。

### R3 · 修正：Letta 的否决理由不成立，但结论可以保留

- **原理由**："Letta 是完整状态化 Agent 运行时，边界大于本产品需要。"
- **问题**：这个理由是错的。Letta 的 **shared memory blocks**（一个 memory block 可 attach 到多个 agent）恰恰是 N+1 场域智能体"共同拥有的记忆"的现成实现——这不是"超出需要"，这**正是**需要。
- **修正后的结论**：结论可以保留，但要换一个站得住的理由——shared memory block 的本质就是一张多个 agent 都能读的共享表，自己实现不难；为此引入一整套有状态 agent 运行时不成比例。因此**降级为可选组件，采用门槛是"需要 agent 自主编辑共享记忆"，而不是"需要共享记忆"。**

### R4 · 修正：过滤式向量检索的风险方向被搞反了

- **原判断**："若 pgvector 在高选择性 ACL + ANN 场景下无法满足召回/时延目标，再迁移到独立向量服务。"
- **问题**：因果反了。高选择性下崩溃的是 **post-filter**；正确做法是 **pre-filter + 对数百个向量做精确检索**，成本微不足道。
- **修正后的结论**：**高选择性恰恰是 pgvector 的舒适区，不是风险场景。** 独立向量库的真实触发条件是"低选择性 + 千万级向量"，单校园不会发生。而且 pre-filter 还是安全要求——先召回后过滤会造成侧信道泄露。

### R5 · 补强：匹配只做优化、不做稳定性

- **原设计**：CP-SAT 求最优组，无稳定性概念。
- **问题**：hedonic coalition game 的基本结论是最优 ≠ 稳定。自愿产品里不稳定的分组会自己散架。
- **补强**：求解后强制稳定性检查（见 [`03-技术架构`](./03-技术架构.md) §8.6），并把它写进成局证明和指标体系。

### R6 · 补强：撮合时机从"兜底"提升为"默认机制"

- **原设计**：固定撮合窗口被列为流动性不足时的补救手段之一。
- **问题**：JPE 2020 的结论说明，在 deadline 可识别的市场里，窗口清算应是**默认**机制，且其收益超过提速。
- **补强**：改为默认机制 + deadline 临近者提前清算，并新增"谎报 deadline"的激励问题为待决项。

### R7 · 补强：正确判断缺少理论出处

- **问题**：早期文档说了"人和关系是事件图谱的投影""保留超边实体"，但没有指出这是 Breiger 二重性 / 超图 / EBSN。结果这些判断读起来像主观偏好，而不是有几十年文献的成熟结论——在评审场合是硬伤。
- **补强**：全部补上出处，见 §1。

### R8 · 补强：自创同意 schema 与"不重复造轮子"红线冲突

- **问题**：早期设计自定义了 consent receipt 与 facet 审批字段。
- **补强**：同意记录结构改为直接采用 ISO/IEC TS 27560:2023 + W3C DPV。**标准复用与开源复用是同一条红线。**

### R10 · 砍掉：校园地图 / 空间发现层

- **原提议**：加一个 L1 校园地图层，把行动机会、进行中的共域和完成事件的痕迹放到地图上，用来补"被看见"这一环。
- **推翻理由**：这是提议方自己发明的需求，不是用户要的（用户说"虚拟校园"时指的是"平台上得有人才能测"，那是仿真人口的需求，见 [`06-仿真与测试人口`](./06-仿真与测试人口.md)）。更关键的判断是成本收益：**一个需要新增一条隐私红线才能安全的功能，本身就说明它的价值配不上代价**。
- **替代方案**：用机会广场（组织者发布的行动机会列表 + 地点作为筛选字段）补"被看见"，95% 的价值、5% 的复杂度。
- **保留的部分**：`place_precision` 作为行动类别注册表的字段保留，由服务端强制降精度——因为提案与机会列表里本来就要显示地点，精度控制是独立于地图的安全需求。

### R11 · 推翻：用端口边界的假实现做测试接缝

- **原提议**：在领域核心的端口边界（`Repository / Extractor / Retriever / Solver / Clock`）做假实现，一条缝覆盖整条链路。
- **推翻理由**：这是单元测试思维。**它会让团队造一堆自己写的假货，最后测的是假货而不是系统。**
- **修正后的策略**：**不使用手写 mock 或 stub 替代自己的任何一层。** 真 PostgreSQL（Testcontainers 跑真迁移）、真 pgvector、真 CP-SAT、真 FastAPI、真 Temporal、真 LLM。**唯一被替换的是"人"。**
- **真正的接缝**：仿真租户（`campus_id` + `is_synthetic`）。它更符合"唯一、最高层、优先用已有的"三条要求——**这条缝本来就因为治理原因必须存在**（不能让真人以为在跟真人配队），测试只是复用它；整个系统在它后面完整运行。
- **两个澄清**：`SimulatedClock` 不是 mock，是可控的真实现，仿真推进真实时间流；CI 中的 LLM 走**录制回放**（真实调用录制一次后重放），是同一个真实现的回放，不是手写假货。

## 6. 相邻产品对照：Tara

[Tara - 懂你的 AI 社交助手](https://apps.apple.com/cn/app/id6743015968)（北京光之域科技，iOS 18+，4.7 分 / 35 条评价）是目前最接近本产品命题的中文产品。它值得单独分析，因为它**独立想到了与我们相近的核心思路，却走向了相反的结局**。

### 6.1 它做对的：Skill Chat 与我们的意图优先撞车

Tara 的副标题是 **「帮你聊 帮你找」**，核心功能叫 **Skill Chat**：

> "围绕你的技能、目标和真实需求发起聊天，找到同样在学、在做、在经历的人"
> "从实习求职、学习计划到生活兴趣，Tara 会帮你把想认识的人和想做的事连接起来"

"围绕真实需求"和"把想认识的人和想做的事连接起来"，与我们「意图优先于画像」几乎是同一句话的两种说法。**这条路线不是我们独有的洞察，有人已经在市场上验证它的吸引力。**

### 6.2 它的用户评价，恰好是我们最该防的失败模式

一个自称"帮你聊帮你找"的产品，用户评价里被反复称赞的是：塔罗占卜准、"被治愈了"、"有人陪真的太好了"、"视为最好的朋友"。

**没有一条评价在说它帮自己找到了人、做成了事。**

这就是分享会点名的虚假繁荣的活体标本——只不过它繁荣的是**陪伴**，不是**连接**。Tara 的功能设计解释了为什么会这样：

- **AI 替你回复**："在别人想和你交谈时，Tara 会用你喜欢的方式替你主动回复并与对方交谈"
- **AI 有自己的生活**："Tara 也有自己的生活，24 小时不间断更新状态，偶尔还会惦记下你"
- **塔罗占卜**：与"帮你找人做事"完全无关的留存工具

前两条正是尤米点名的送命题；第三条的存在本身说明**连接功能撑不起留存，必须靠陪伴补**。

> **可执行推论**：让用户对 AI 本身产生依恋的设计会稀释北极星。这不是说 AI 不能帮忙聊天——**帮忙聊和被依恋是两件事**。区别在于 AI 服务的是"这段关系往前走"还是"用户和 AI 待在一起"。前者做完就退场，后者要求用户回来找它。

因此可以做的：帮起草、帮破冰、帮把话说清楚、在用户忙时代为回应。应当避免的：模拟自己的生活、主动惦记用户、发展出可供依恋的人格。见 [`07-产品语言与界面原则`](./07-产品语言与界面原则.md) 原则四。

### 6.3 值得学的四点（呈现层）

| 学什么 | Tara 怎么做 | 我们怎么用 |
|---|---|---|
| **一句话说清做什么** | 副标题「帮你聊 帮你找」——两个动词，四个字 | "共域 CoField" 完全没做到。对外名与副标题需要动宾结构，见 07 §8 |
| **用具体场景代替抽象描述** | "从实习求职、学习计划到生活兴趣" | 我们的意图面目前是一个空输入框。**冷启动用户面对空框会卡住**，首屏应给场景引子 |
| **给功能起动词化的名字** | Skill Chat | 比"成局提案"这类名词化术语更容易被理解 |
| **低门槛的半成形表达** | 状态发布，随手记一句 | 我们的漏斗要求用户"已经想清楚"。补一个**念头暂存**：还没想清楚也能先说一句 |

### 6.4 明确不学的五点，以及为什么我们更好

| 不学什么 | 我们的做法 | 依据 |
|---|---|---|
| **AI 代聊而对方不知道** | 代聊本身可做（见 §6.6），但是否披露是**可配置策略**，不是隐瞒 | 《人工智能生成合成内容标识办法》要求显式或隐式标识；且研究结论是 AI 代写**被感知时**削弱评价——隐瞒是推迟伤害不是避免 |
| AI 替人做出承诺或确认 | 七种协商消息**没有一种构成同意**；承诺状态只接受真人签名 | 分享会："Agent 应帮助关系预热，但不能替人完成最重要的确认或投入" |
| AI 有自己的生活、24 小时惦记你 | 场域智能体在角落、说话短、不主动弹窗、不模拟生活 | 北极星是完成的共同事件数，不是陪伴时长 |
| 塔罗占卜等无关留存工具 | 留存来自"总有事情可以一起做" | 需要靠无关功能补留存，说明主功能没跑通 |
| 基于兴趣标签配对 | 意图 + 硬约束 + 群体求解 + 稳定性检查 | 兴趣相似不等于能一起把事做成 |
| AI 记住你的故事、了解你的喜好（记忆归个人） | 记忆归属事件与关系，有来源、可撤销、多方审批 | 二重性原理；且"关系资产"必须是共同拥有的 |

### 6.5 代聊模式：把它做成策略，而不是禁令

Tara 的"AI 替你回复"验证了一个真实需求：**很多人不是不想连接，是不想开口**。慢热的人、社恐的人、忙起来顾不上回消息的人，都需要有人替他先接上话。这个需求不该被一条红线砍掉。

设计空间有三档，产品可以按场景选，不必全局锁死：

| 档位 | 谁在说 | 对方看到什么 | 适用场景 |
|---|---|---|---|
| **本人** | 真人 | 正常消息 | 默认 |
| **AI 起草，本人过目** | 真人（内容由 AI 拟） | 正常消息 | 慢热、不知怎么开口 |
| **AI 代答** | AI | 取决于披露策略 | 本人忙、时区不便、只是先接住话头 |

真正需要决定的只有一件事：**第三档要不要让对方知道，以及怎么让对方知道而不尴尬。**

三个可选实现，成本递增：

1. **常态化轻标识**——消息旁一个极轻的标记，不弹窗不打断。**关键在于它是常态**：当所有人都知道 AI 可以帮忙接话，用 AI 就不再是丢人的事，也就不存在"被发现"那一刻。
2. **仅在关键时刻披露**——日常代答不标，但涉及承诺、披露、见面时强制切回真人并提示。
3. **完全不披露**——合规上要正面回答《人工智能生成合成内容标识办法》的适用性，且要接受"被发现时"的关系代价。

**架构上三档都支持**，选哪档是行动类别注册表里的一个策略字段（`agent_reply_policy`），可按校园、场景、风险层不同配置。**这条不写进领域不变量。**

不变的只有一条：**AI 无论说了多少话，都不能产生承诺**。承诺状态只接受真人签名的命令——这是产品能否成立的底线，与代聊无关。

### 6.6 一处结构性差异

Tara 有"自定义个人主页与虚拟形象"，小火人也有形象养成——说明年轻用户确实吃这一套。我们明确不做**对外展示主页**，但我们有等价物，而且归属不同：

> 形象归属**共同体**（场域智能体属于这次事件的 N 个人），不归属个人。

这恰好是我们相对二者的结构性优势：小火人的形象挂在 pairwise 边上（5 个朋友养 5 只），Tara 的形象挂在个人上（又一张名片），我们的挂在超边上。
