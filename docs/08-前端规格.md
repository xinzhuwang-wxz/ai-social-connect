# 共域 CoField · 前端规格

- 目的：让前端与后端、数据库三层从第一天就对齐，避免"各层单看都对、跑起来 422"
- 参照：[Tara](https://apps.apple.com/cn/app/id6743015968) 的呈现方式（轻量、极简、低门槛），按本产品需要调整
- 方法论参照 [coherent-fullstack-skill](https://github.com/xinzhuwang-wxz/coherent-fullstack-skill) 的契约先行部分
- 文案规则见 [`07-产品语言与界面原则`](./07-产品语言与界面原则.md)；后端契约见 [`03-技术架构`](./03-技术架构.md) §10

> **可信度说明**：Tara 的视觉细节来自应用商店的文字描述与第三方产品页，**未直接查看界面截图**。视觉语言部分属于推断，拿到截图后应校准。屏幕清单与数据契约部分不依赖 Tara，是从本产品的领域模型推出的，可以直接施工。

## 1. 对齐三原则（这一节决定开发顺不顺）

**① 类型不手写，一层都不手写。**

```
Pydantic v2 领域 schema
      ↓  FastAPI 自动导出
OpenAPI 3.1
      ↓  codegen
前端 TypeScript 类型
```

任何手写的前端接口类型都是缺陷。CI 检测到 `interface` 与生成产物不一致即失败。

**② 一个概念，三层同名。**

命名唯一来源是 [`CONTEXT.md`](../CONTEXT.md)。数据库 `event_participations.principal_id`、API `principal_id`、前端 `principalId`（仅大小写风格转换，由 codegen 统一处理）。**不做层间语义翻译**——不允许后端叫 `principal`、前端叫 `user`。

**③ 界面文案与字段名是两套东西。**

字段名用领域词汇（`formation_proof`），界面文案用用户词汇（"为什么是这几个人"）。映射见 07。**这不违反 ②**：② 管的是字段标识符，③ 管的是给人看的字符串。

## 2. 视觉语言

从 Tara 借的三条（**推断，待截图校准**）：

| 借什么 | 我们的调整 |
|---|---|
| 轻量、极简、低信息密度 | 我们的信息密度天然更高（成局证明有 6 条依据 + 3 条待决 + 不确定性）。做法是**分层折叠**：默认只显示结论行，点开看依据，而不是把密度降下来丢掉可信度 |
| 趣味化破冰辅助 | 用在意图输入和等待期，**不用在确认门和回声审阅**——那两处需要用户认真 |
| 图文混排的卡片看板 | 我们的卡片必须携带来源与时效，不能是纯展示卡 |

不借的：塔罗等仪式化留存组件、24 小时更新的 AI 状态流、可浏览的个人主页。

### 2.1 设计令牌

```
圆角      卡片 16 / 内部元素 8 / 按钮 12
间距      4 的倍数；卡片内 16，卡片间 12，分组间 24
字号      标题 20 / 小标题 16 / 正文 15 / 辅助 13 / 标签 11
行高      正文 1.6（中文密排需要）
主色      单一强调色，只用于「主操作」和「待你决定」
语义色    确认=中性绿 / 待定=琥珀 / 冲突=红 / AI 草稿=灰紫
```

**AI 草稿必须有独立的视觉通道**（灰紫 + 虚线边框），与人工确认内容一眼可辨——这是 07 原则一的强制要求，不是装饰。

### 2.2 三种卡片

| 卡片 | 用在哪 | 必含元素 |
|---|---|---|
| **依据卡** | 成局证明、经历证据 | 结论行 + 可展开的来源 + 时效 |
| **决定卡** | 授权、确认门、回声审阅 | 一个问题 + 二到三个选项 + 影响说明 |
| **状态卡** | 我的事件、机会列表 | 标题 + 关键时间 + 当前状态 + 下一步入口 |

## 3. 屏幕清单与数据契约

每屏列出：读什么、发什么命令、有哪些状态。**这张表是前后端的联合施工依据。**

### 3.1 意图面 · 「想做点什么」

| 项 | 内容 |
|---|---|
| 读 | `GET /action-kinds`（场景引子）·`GET /intents/{id}`（回看草稿） |
| 写 | `POST /intents:compile`（自然语言→结构化）·`PATCH /intents/{id}`（用户修改）·`POST /intents/{id}:confirm` |
| 空态 | **不是空输入框**——见 §4 |
| 加载 | 编译中显示逐字段浮现，不显示转圈 |
| 错误 | 抽取失败 → 展示原文 + 手填表单，流程不中断 |
| 冲突 | 硬约束自相矛盾 → 指出是哪两条冲突，不泛泛说"输入有误" |
| 对应 issue | #2 |

### 3.2 授权面 · 「这次让他们看到什么」

| 项 | 内容 |
|---|---|
| 读 | `GET /intents/{id}/envelope-candidates`（可授权字段清单及其用途）·`GET /me/facets?matching_allowed=true` |
| 写 | `PUT /intents/{id}/envelope`·`POST /envelopes/{id}:revoke` |
| 关键呈现 | 每项右侧常驻显示「仅用于求解」/「对方可见」；顶部常驻显示有效期 |
| 特殊态 | 零历史用户看不到「允许引用的经历」分组，而不是看到一个空分组 |
| 对应 issue | #3 |

### 3.3 等待面 · 「明早 8 点开始配队」

| 项 | 内容 |
|---|---|
| 读 | `GET /market-units/{id}/status`（下次清算时间、当前池深度、席位缺口） |
| 写 | `PATCH /intents/{id}`（窗口开始前仍可改） |
| 关键呈现 | 倒计时 + 当前方向有多少人多少机会。**这是最容易被做成空白页的一屏** |
| 特殊态 | 截止期临近者显示「你的截止时间近，会被提前处理」 |
| 对应 issue | #7 |

### 3.4 提案面 · 「给你找的人」

| 项 | 内容 |
|---|---|
| 读 | `GET /intents/{id}/proposals`（2–3 个，每个含 `formation_proof` 机器可读结构） |
| 写 | `POST /proposals/{id}:respond`（接受/条件接受/拒绝/换一组） |
| 关键呈现 | 默认折叠成六行结论；点任一行展开来源。**界面上不得出现任何百分比** |
| 空态 | 无可行解 → 阻塞证明（哪几条约束冲突 + 放宽各能多几人 + 订阅） |
| 对应 issue | #6 #15 |

### 3.5 受邀面 · 「这次你会得到什么」

| 项 | 内容 |
|---|---|
| 读 | `GET /invitations/{id}`（互惠视角：付出、获得、发起方验证状态） |
| 写 | `POST /invitations/{id}:respond`（含条件接受的结构化条件） |
| 关键呈现 | 拒绝按钮与接受同等视觉重量，**不做成灰色小字** |
| 对应 issue | #8 |

### 3.6 确认面 · 「还差这几件事」

| 项 | 内容 |
|---|---|
| 读 | `GET /proposals/{id}/open-decisions`（只返回未决项）·`GET /proposals/{id}/confirmations` |
| 写 | `POST /proposals/{id}:confirm`（带版本号，幂等键必填） |
| 关键呈现 | 已决部分默认折叠；实时显示还在等谁 |
| 关键约束 | 版本变化后前端必须重新拉取并要求重新确认，**不允许用旧版本提交** |
| 对应 issue | #9 |

### 3.7 空间面 · 项目自己的名字

| 项 | 内容 |
|---|---|
| 读 | `GET /spaces/{id}`（对象图）·实时频道（Presence、正在编辑） |
| 写 | `POST /spaces/{id}/objects`·`PATCH /space-objects/{id}`·`POST /artifacts` |
| 关键呈现 | 结构化画布为主，聊天在侧栏。助手固定在右下角卡片，**不占据主区** |
| 降级 | 实时频道断开 → 顶部一行提示 + 轮询；助手不可用 → 助手卡片显示不可用，其余全部照常 |
| 对应 issue | #10 #11 |

### 3.8 回声面 · 「这次留下了什么」

| 项 | 内容 |
|---|---|
| 读 | `GET /events/{id}/echo-draft`（逐条草稿 + 每条的审批需求） |
| 写 | `POST /echo-claims/{id}:approve`·`:reject`·`PATCH`（改措辞） |
| 关键呈现 | 每条独立卡片；关系切面显示「需要 A、B、C 都点头」及当前进度 |
| 关键约束 | 跳过整屏不影响事件完成状态，界面要明说这一点 |
| 对应 issue | #12 |

### 3.9 我的记录 · 三个自我管理面

| 项 | 内容 |
|---|---|
| 读 | `GET /me/events`·`GET /me/facets`·`GET /me/grants`·`GET /me/preview?action_kind=` |
| 写 | `POST /facets/{id}:revoke`·`:stop-matching`·`PATCH`（改措辞）·`POST /me/export`·`POST /grants/{id}:revoke` |
| 关键呈现 | 撤销是主按钮不是二级菜单；关系切面撤销前提示会通知谁 |
| 特殊屏 | 「别人眼中的我」——选一个行动类别，看到自己会被展示的字段 |
| 对应 issue | #13 |

### 3.10 机会面 · 组织者两屏

| 项 | 内容 |
|---|---|
| 读 | `GET /opportunities`（学生侧）·`GET /orgs/{id}/opportunities`（组织者侧，含席位缺口） |
| 写 | `POST /opportunities`·`PATCH /opportunities/{id}` |
| 关键呈现 | 学生侧必须显示「已验证组织」标识；组织者侧只显示成员授权范围内的候选信息 |
| 对应 issue | #4 |

## 4. 首屏不能是空输入框

这是 Tara 给的最实用的一条启发。它用"从实习求职、学习计划到生活兴趣"把抽象需求具体化；我们的意图面目前只有一句"你想做点什么？"加一个空框——**冷启动用户面对空框会卡住，这是漏斗第一段最大的流失点**。

改成场景引子，数据来自行动类别注册表（`GET /action-kinds`），**新增一个行动类别时首屏自动多一张卡，不改前端代码**：

```
┌──────────────────────────────────┐
│  想做点什么？                     │
│                                  │
│  ┌────────┐ ┌────────┐ ┌───────┐ │
│  │ 比赛组队│ │ 课程项目│ │作品创作│ │
│  └────────┘ └────────┘ └───────┘ │
│  ┌────────┐ ┌────────┐           │
│  │ 学习搭子│ │ 实习互助│           │
│  └────────┘ └────────┘           │
│                                  │
│  ─────────  或者直接说  ────────  │
│  ┌──────────────────────────────┐│
│  │ 比如：想拍个一分钟短片，周五前││
│  │ 完成，我会写脚本但不会剪...  ││
│  └──────────────────────────────┘│
└──────────────────────────────────┘
```

输入框的 placeholder 是**一个完整的好例子**，不是"请输入…"。它同时起到了示范作用——告诉用户什么样的表达能被接住。

## 5. 状态矩阵

每屏都必须实现这五态，**缺一个就是缺陷**：

| 态 | 要求 |
|---|---|
| 首次 | 有引导，不是空白 |
| 加载 | 骨架屏，不是转圈；长任务显示当前阶段 |
| 空 | 说明为什么空 + 一个可执行的下一步 |
| 错误 | 说清哪里错了 + 怎么继续，不出现错误码 |
| 降级 | 后端某个能力不可用时，其余功能仍可用并明示 |

降级这一列是本产品特有的：LLM、向量、实时、助手任一挂掉，用户都必须还能保存意图、看空间、人工确认、上传证据。

## 6. 组件清单

优先用 Radix / shadcn 原语，**不自研交互与无障碍基础**。需要自建的只有四个，都是领域特有的：

| 组件 | 为什么必须自建 |
|---|---|
| `EvidenceRow` | 结论 + 可展开来源 + 时效，全项目复用（成局证明、经历证据、记忆卡） |
| `DecisionGate` | 一个问题 + 选项 + 影响说明 + 谁还没确认，且必须阻止 AI 越过 |
| `SpaceCanvas` | React Flow 之上的领域节点（目标核、席位、决策门、素材卡、回声卡） |
| `DraftBadge` | AI 草稿的统一视觉通道，全局唯一实现，防止各处自行发挥 |
