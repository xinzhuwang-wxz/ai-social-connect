## Problem Statement

一个大二学生想拍一支校园短片投比赛，周五截止。会写脚本，不会拍也不会剪，不认识合适的人。

她能做的事只有这些：在校园墙发帖、在班级群里问、在小红书发"求队友"。这些渠道的共同问题是——

**说不清楚自己要什么。** "找个会拍视频的"这句话对方看不出该不该回应，因为它没说时间、没说要做什么、没说对方能得到什么。

**发出去就没了。** 帖子刷过去就沉了。看到的人多半不在同一个校区、那几天没空、或者根本不做视频。真正合适的那三个人可能压根没刷到。

**对方不知道你靠不靠谱。** 一个陌生同学收到私信，第一反应是"这人是不是骗子"，第二反应是"加了之后要干嘛"。

**联系上了也不知道下一步。** 拉了个群，寒暄两句，然后群就沉了。谁负责什么、什么时候开工、署名怎么算，没人先开口。

**做完了什么都没剩下。** 就算真拍出来了，这件事对下一次组队毫无帮助——她的能力没有任何可信的记录，那两个人下次也不会被优先想起。

反过来，一个会剪辑的大三学生同样卡住：他想找作品练手，但他不知道谁需要剪辑，也不想把自己挂在一个"技能展示墙"上被陌生人挑。

**校园里不缺人，缺的是把"我想做件事"变成"我们真的一起做成了"的通路。**

---

## Solution

一个平台，学生只需要说一句话——"我想做个校园流浪猫的一分钟短片，周五前完成，我会写脚本但不会拍不会剪"。

系统把这句话整理成一张可检查的卡片（做什么、能给什么、缺什么、什么时候、在哪、什么底线），让她确认。然后她逐项勾选这次愿意让别人看到什么。

不是立刻推人。系统在一个撮合窗口里攒够意图后统一算一次，给她**两个小队**，每个小队附一份**为什么是这几个人**：角色怎么覆盖的、时间在哪几个交集、地点可不可行、证据从哪来、每个人各自得到什么、以及"这几个人现在都没有更想去的组"。没有匹配百分比。

另一侧的剪辑同学收到的不是"有人想加你"，而是"这次你会得到什么"——付出多少小时，换回一支可署名的完成作品。他可以说"我可以，但周四要 16 点之后"。

三个人在一个只放**未决事项**的界面上碰头：公开发布吗、署名怎么排、能不能拍到人脸。全部确认后，一个属于这次事件的空间才被创建——不是聊天群，是一张能看见目标、角色、时间线、卡在哪里的画布，角落里有一个只服务这件事的助手。

片子交了之后，助手把散落的证据聚成一份草稿，逐条问：这条能不能留？留了之后，"完成 60 秒纪录短片的剪辑与调色"就带着来源、有效期和撤销开关，存在剪辑同学自己的记录里。两周后他发起新组队时，系统会说"你们上次一起完成过《檐下》"。

**AI 退出之后，剩下的不是聊天记录，是一支有三个人署名的片子、一个还在的空间、一条可撤销的能力证据，和下一次一起做事的具体理由。**

## User Stories

### 表达意图

1. 作为一个从没用过这个产品的学生，我想直接说一句话就开始，不用先填资料，这样我不会在注册页就放弃。
2. 作为发起者，我想看到系统把我的话整理成什么样，并能改，这样我能确认它没理解错。
3. 作为发起者，我想只被问一两个真正影响结果的问题，这样我不用做问卷。
4. 作为发起者，我不想被问性格、MBTI 或完整履历，这样我不会觉得在填相亲表。
5. 作为表达能力一般的学生，我想说得含糊时系统能追问，说不清时能退回手填表单，这样我不会卡死。
6. 作为发起者，我想给我的需求设一个截止时间，这样系统知道我什么时候不需要了。
7. 作为发起者，我想随时撤回还没成局的意图，这样我改主意时没有负担。
8. 作为发起者，我想看到我的意图什么时候过期，这样我知道要不要续。

### 决定露出什么

9. 作为发起者，我想逐项勾选这次让别人看到我的什么，这样我不是一次性交出一份档案。
10. 作为发起者，我想知道每一项是"给系统算"还是"会展示给候选人"，这样我心里有数。
11. 作为发起者，我想看到这次授权多久失效，这样我不用担心它永久生效。
12. 作为有过往经历的学生，我想选择这次允许引用哪几条经历，这样我不是被自动翻旧账。
13. 作为发起者，我想预览"别人在提案里会看到我的什么"，这样最小披露对我是可检查的，不是一句承诺。

### 等待与撮合

14. 作为发起者，我想知道下一次配队什么时候开始，这样我不会以为系统坏了。
15. 作为发起者，我想知道当前这个方向有多少人和多少机会，这样我对结果有预期。
16. 作为截止时间很近的发起者，我想被优先处理，这样我不会因为等窗口而错过。
17. 作为发起者，我想在没算出结果时收到明确说明，而不是空白页。

### 看提案

18. 作为发起者，我想只看到两三个提案，这样我能真的做决定而不是无限翻。
19. 作为发起者，我想看到"为什么是这几个人"，这样我知道该不该信。
20. 作为发起者，我想看到时间到底在哪几个交集，这样我能立刻判断可行性。
21. 作为发起者，我想看到某个人的经历证据来自哪一次事件，这样它不是一句自吹。
22. 作为发起者，我想看到每个人各自能得到什么，这样我知道这不是单方面占便宜。
23. 作为发起者，我想知道这几个人现在有没有更想去的组，这样我知道队伍稳不稳。
24. 作为发起者，我不想看到匹配百分比或"灵魂队友"这类说法，这样我不会被无法检查的分数糊弄。
25. 作为发起者，我想看到系统承认的不确定性，这样它对我是诚实的。
26. 作为发起者，我想看到哪些事必须我们自己决定，这样我知道系统没越界。
27. 作为发起者，我想看到这个提案什么时候失效，这样我知道要不要现在处理。
28. 作为发起者，我想能说"换一组"，这样我不是只能二选一。

### 被邀请一侧

29. 作为候选参与者，我想看到的是"这次我会得到什么"，而不是"有人想加你"，这样我能判断值不值。
30. 作为候选参与者，我想看到我要付出多少时间，这样我不会在承诺之后才发现超出预期。
31. 作为候选参与者，我想在不透露更多身份的前提下先做判断，这样我不用先暴露自己。
32. 作为候选参与者，我想说"我可以，但有条件"，这样我不用在接受和拒绝之间二选一。
33. 作为候选参与者，我想拒绝时不用写理由，这样拒绝没有心理负担。
34. 作为候选参与者，我想确认我的拒绝不会被告诉其他候选人，这样我不担心被报复。
35. 作为候选参与者，我想确认拒绝不会降低我以后的匹配机会，这样我可以放心说不。
36. 作为候选参与者，我想控制我的哪条经历可以被引用，这样别人不能替我引用。
37. 作为经常被邀请的人，我想有一个并发上限，这样我不会被淹没。

### 真人确认

38. 作为参与者，我想在确认界面上只看到还没定的事，这样我不用重读已经谈好的部分。
39. 作为参与者，我想看到每个人分别负责什么，这样我知道自己要做什么。
40. 作为参与者，我想和大家一起定第一个具体动作，这样散会之后有下一步。
41. 作为参与者，我想看到还有谁没确认，这样我知道在等谁。
42. 作为参与者，我想在有人改了实质内容后重新确认，这样我不会被偷偷改条件。
43. 作为参与者，我想在所有人确认之前，这件事都还不算数，这样我不会被半途绑定。
44. 作为参与者，我想署名、是否公开、能不能拍人脸这类事永远由我们自己决定，这样 AI 不能替我做主。

### 项目空间

45. 作为已成局成员，我想一眼看到我们要做什么、谁负责什么、现在卡在哪，这样我不用翻聊天记录。
46. 作为已成局成员，我想看到时间线和下一个节点，这样我知道什么时候该动。
47. 作为已成局成员，我想认领和更新任务，这样进度是共享的。
48. 作为已成局成员，我想上传素材并保留来源，这样成果有据可查。
49. 作为已成局成员，我想看到还有哪些决定没关闭，这样它们不会被忘掉。
50. 作为已成局成员，我想助手提醒我而不是替我决定，这样我保持掌控。
51. 作为已成局成员，我想助手待在角落，这样它不抢主界面。
52. 作为已成局成员，我想助手的每个建议都能一键说"不用了"，这样它不烦人。
53. 作为已成局成员，我想确认助手看不到我和别人的私聊，这样我有安全感。
54. 作为已成局成员，我想在助手挂掉时仍能上传、认领、确认，这样核心流程不依赖 AI。
55. 作为中途要退出的成员，我想能体面退出并触发补位，这样不是一走了之。
56. 作为负责人，我想在自己带不动时移交，这样项目不会烂尾。

### 留下什么

57. 作为参与者，我想在结束时看到一份草稿而不是空白框，这样我不用从零写。
58. 作为参与者，我想逐条决定留不留，这样不是打包接受。
59. 作为参与者，我想改措辞，这样记录是我认可的说法。
60. 作为参与者，我想直接说"不留"，这样我可以完全不留痕。
61. 作为参与者，我想确认跳过回声不会影响这件事算不算完成，这样它是可选的。
62. 作为被描述的人，我想只有我本人能确认关于我的能力描述，这样别人不能替我背书。
63. 作为共同经历的一方，我想描述我们几个人的记录需要所有人点头，这样没人能单方面定义我们的关系。
64. 作为有不同意见的人，我想标记异议并让这条暂停使用，这样冲突不会被压成"已通过"。
65. 作为参与者，我想看到 AI 猜的和人确认的在视觉上完全不同，这样我不会把推测当事实。

### 我的记录（自我管理面）

66. 作为用户，我想看到系统记住了关于我的什么，这样它对我不是黑箱。
67. 作为用户，我想看到每一条记录来自哪次事件、哪个证据，这样它可追溯。
68. 作为用户，我想看到每一条谁能看到、用在什么地方、什么时候过期，这样我知道它的影响范围。
69. 作为用户，我想停止某条记录用于匹配但保留它，这样我有中间选项。
70. 作为用户，我想撤销某条记录，操作应该像删一条动态那么简单，这样我真的会去用这个权利。
71. 作为用户，我想在撤销涉及别人的记录时被提示会通知谁，这样我不会误伤。
72. 作为用户，我想导出我的全部记录，这样数据是我的。
73. 作为用户，我想看到我参加过哪些事、哪些完成了哪些取消了，这样我能看到自己的轨迹。
74. 作为用户，我想看到取消的事不产生任何"成功"记录，这样系统对我诚实。
75. 作为用户，我想看到哪些授权还生效并能一键收回，这样我不会有忘掉的口子。
76. 作为用户，我不想有一个供别人浏览的个人主页，这样我不会被当成卡片挑选。

### 组织者（最小能力）

77. 作为社团负责人，我想发布一个带席位和角色的招募，这样学生能对着具体缺口来。
78. 作为组织者，我想设定截止时间和资格要求，这样来的人是对的人。
79. 作为组织者，我想看到每个席位还缺几个人，这样我知道要不要补推。
80. 作为组织者，我想只看到候选人为完成这件事必须让我知道的信息，这样我不越权。
81. 作为组织者，我想我的身份被验证过，这样学生敢信我。
82. 作为学生，我想看到发布方是被验证过的组织，这样我不担心是骗局。

### 冷启动与失败路径

83. 作为凑不出队的发起者，我想知道具体卡在哪一条，这样我知道能改什么。
84. 作为凑不出队的发起者，我想知道放宽某一项能多出多少人，这样我的取舍是有依据的。
85. 作为凑不出队的发起者，我想知道哪些条件涉及安全不建议放宽，这样我不会为了成局牺牲底线。
86. 作为凑不出队的发起者，我想订阅"有人符合时通知我"，这样我不用反复回来看。
87. 作为零历史的新用户，我想和老用户有同样的成局机会，这样我不会因为新而吃亏。

## Implementation Decisions

### 领域与存储

- **权威事实只在 PostgreSQL 18+。** 向量、图投影、搜索、Agent 记忆全部是可重建派生物。禁止用"向量库里搜得到"证明用户已同意。
- **事件是一等公民，人是投影。** `events` + `event_participations` 构成超边；人-人关系是物化视图，不作为原始数据存储。不存"好友度""熟悉度"字段。
- **记忆切面是长期记忆的唯一形态。** `facets(subject_type: person|relationship|collective, claim, source_episode_ids[], visibility, matching_allowed, approval_state, valid_time, record_time)`。没有"个人 Markdown 档案"这种对象。
- **切面有效期用 PG 18 原生时序约束。** `PRIMARY KEY (id, valid_time WITHOUT OVERLAPS)`；system time 用 `record_time tstzrange` + 触发器，不引入 `periods` 扩展。
- **图查询用递归 CTE + 物化视图。** 本 PRD 范围内不启用 Apache AGE，不引入任何独立图数据库。
- **`episodes` 表承载原始事实流**，每条派生切面必须能追溯到至少一条 episode。

### 时间与仿真

- **领域核心不得调用 `now()`。** 新增 `Clock` 端口，三个实现：`SystemClock` / `SimulatedClock` / `FrozenClock`。意图 TTL、撮合窗口、切面有效期、提案过期、工作流等待全部走它。**这是本 PRD 的前置项，必须在写任何领域代码之前落地。**
- **新增 `principals.is_synthetic`。** 领域不变量：合成主体与真人不得进入同一成局提案。仿真跑在独立 `campus_id`。界面上合成主体可见标记。

### 撮合流水线

五段漏斗，量级 `20000 → 数百 → 数十 → 2–3 提案`：

1. **权限 + 硬约束过滤（SQL）** —— 租户、屏蔽、时间窗、校区、人数、必要角色、并发上限。硬约束是过滤器，**不参与打分，任何软分不得抵消冲突**。
2. **混合召回** —— 供需倒排 + pgvector 语义 + 事件图 + 组织席位。召回通道是可插拔的 `Retriever` 实现。
3. **CP-SAT 群体求解** —— 求解对象是 `best_group | intent, constraints, consent, reciprocal_value, market_state, safety`，不是 `similarity(A,B)`。
4. **稳定性检查** —— 对每个成员验证不存在"他更偏好且愿接纳他"的其他候选组（Nash 稳定近似）。**这是硬门槛，不是优化项：未通过的分区不得提交为提案**，需重新求解或降级为更小但稳定的组。
5. **互惠确认** —— 多方接受才算成功。

- **撮合按固定窗口清算**，窗口长度由行动类别注册表声明；deadline 临近成员单独提前贪心处理。**不是即时匹配**。
- **向量检索必须 pre-filter。** ACL 与硬约束先执行再做向量比较。理由有二：post-filter 在高选择性下召回崩塌；先召回后过滤会造成侧信道泄露。同类查询设披露预算。

### 意图编译

- LLM 负责自然语言 → 严格 schema 并标注不确定字段；**确定性校验**负责类型/枚举/时间解析、敏感信息检测、硬约束自相矛盾检查。
- **未经用户确认的抽取不得进入匹配。** 原始表达与结构化结果并存。
- 用 Instructor（Pydantic 校验 + 自动重试），**不自研 JSON 修复与重试循环**。

### 成局证明

- LLM 只能把确定性求解结果**转写**成自然语言，不得自行发明理由。每条理由必须引用：本次用户表达 / 获准切面 / 求解器满足的约束 / 可解释目标项 / 未解决冲突，五者之一。
- 证明对象保留**机器可读结构**，不能只存一段生成文本。
- **禁止输出总分、百分比或不可检查的结论。**

### 协商

- 第一方 agent 走**内部领域命令**，本 PRD 不启用 A2A 网络协议。
- 只允许七种固定消息：`ConstraintIntersection` / `EvidenceCitation` / `ConditionalResponse` / `Conflict` / `ProposalRevision` / `DisclosureDenied` / `ConsentRequest`。**没有一种构成同意。** 自由文本只作字段补充。
- 协商过程本身不得产生长期记忆。

### 确认与事务

- 确认是**版本化、多方、可撤回**的。条件接受生成新版本，不隐藏修改。
- 达到门槛后，**同一事务内**写入承诺 + 创建共同事件 + 成员关系 + 共域；事务提交后才生成场域智能体授权。
- **不允许提案"部分成立"。**
- 所有写操作幂等：`idempotency_key = actor + command_type + aggregate_id + client_request_id`。

### 共域与场域智能体

- 主界面是**结构化画布**（React Flow），不是聊天记录。空间对象：目标核、成员席位、任务、决策门、素材卡、行动轨迹、回声卡、下一步种子。
- 场域智能体是**能力令牌驱动**的，不是无限工具权限。允许 `draft_*` / `read_approved_*` / `request_member_decision` / `ingest_external_artifact` / `propose_memory_facets`；`change_commitment` / `invite_or_remove_member` / `publish_artifact` / `approve_memory` 永远需要真人。
- 它**不继承任何成员的私有记忆**，存储命名空间与其他共域隔离。
- **场域智能体不可用时，共域核心功能必须仍然可用。**

### 记忆回流

- 回声草稿由证据聚合生成，`approval_state` 默认 `draft`。
- 审批规则：描述个人 → 本人确认；描述关系 → 所有被描述者确认；有异议 → `contested`，停止进入新匹配。四态：`contested` / `redacted` / `withdrawn` / `superseded`。
- 撤销**先阻止新用途**（权威服务即时生效），再异步清理派生索引，目标 < 5 min。
- 取消的事件保留审计但**不产生关系边、不产生成功记忆**。

### 自我管理面

- 三个面全部是**读模型 + 已有的授权/撤销命令**，领域模型不新增聚合。
- 后端只需新增查询端点。**不新增"用户档案"聚合根**。
- 提供"别人眼中的我"预览端点：给定一个行动类别，返回本人在该场景成局证明中会被展示的字段集合。

### 组织者（最小能力）

- 新增 `organizations` / `organization_memberships` / `action_opportunities` / `opportunity_seats`。
- 组织者角色是**事件级权限**，不是全局身份。
- 本 PRD 只做"发布带席位的机会 + 查看席位缺口"，不做模板、候补、移交、分析。

### 扩展点

- **行动类别注册表**：`intent_schema_ext` / `hard_constraints` / `soft_objectives` / `seat_model` / `risk_tier` / `place_precision` / `echo_template` / `matching_window`。
- 判定标准：**新增一个行动类别不得修改领域核心的任何文件。**
- `place_precision` 由服务端强制降精度后输出，客户端无权提升。系统展示的永远是事件地点，不是人的位置。

### 契约与前端

- **Pydantic v2 领域 schema → FastAPI 导出 OpenAPI 3.1 → 前端类型自动派生。任何一层都不手写类型。**
- 一个概念在 DB / API / 前端用同一个名字，命名来源是 `CONTEXT.md`。
- 所有状态必须能通过版本化 API 完整获取；实时通道是增强而非必需。
- **用户可见文案不得出现领域词汇**，映射表见 07。CI 加术语黑名单检查，例外白名单限于申诉、导出、争议处理三处。

### 求解对象的 schema 片段

以下形状编码了一个关键决定——求解目标是组而不是对：

```python
class FormationRequest:
    intent: IntentSignal
    candidates: list[CandidateEnvelope]     # 已过 ACL 与硬约束
    hard_constraints: list[HardConstraint]  # 过滤器，不进目标函数
    objectives: list[WeightedObjective]     # 可独立解释、可插拔
    market_state: MarketState               # 曝光拥挤、并发承诺
    safety_policy: SafetyPolicy

class FormationResult:
    groups: list[CandidateGroup]
    proof: FormationProof                   # 机器可读，非文本
    stability: StabilityVerdict             # PASS 才允许成为提案
    blocked_by: list[HardConstraint] | None # 无解时返回
```

## Testing Decisions

### 什么是好测试

只测**外部行为**，不测实现细节。判据：换掉一个适配器（LLM、向量后端、求解器实现）不应导致任何领域测试失败。如果失败了，说明测试测的是实现。

### 测试接缝

**首选接缝是领域核心的端口边界**，只此一处：

```
Repository / Extractor / Retriever / Solver / PolicyEngine / EventPublisher / Clock
```

在这一层做假实现，一条缝覆盖整条链路——不需要真 LLM、不需要真求解器、不需要真数据库。

这不是为测试新造的缝，它本来就是架构的依赖边界（[`03-技术架构`](../03-技术架构.md) §4），测试只是复用它。

不新增其他接缝。UI 层不做单元测试接缝，用端到端流程覆盖。

### 必须测的领域不变量

1. 任一硬约束冲突不能被高软分抵消
2. 未获真人确认的提案不能创建事件、共域或关系边
3. 提案关键字段变化会使旧同意失效
4. 成局证明的每个事实都能追溯到输入、切面或求解结果
5. 未批准或已撤销切面不能进入新召回
6. 取消/过期提案不形成关系投影
7. 删除源素材会失效或复核依赖切面
8. 一名成员不能替其他成员批准共同记忆
9. 场域智能体不能读取未共享的私有记忆
10. **稳定性检查未通过的分区不会被提交为提案**
11. **合成主体不会与真人进入同一提案**
12. **新增一个行动类别不需要修改领域核心文件**
13. **领域核心中不存在对 `now()` 的直接调用**（静态检查）

### 时间相关测试

用 `FrozenClock` 测 TTL、过期、有效期边界；用 `SimulatedClock` 测跨窗口撮合与跨天工作流。**不允许用 sleep 测时间行为。**

### 契约测试

每个前端消费者对领域 API 有契约测试，破坏性变更在 CI 失败。OpenAPI 由领域 schema 生成，不手写。

### 术语泄漏检查

CI 扫描所有用户可见文案（i18n 资源、组件字面量），命中 `CONTEXT.md` 术语黑名单即失败。白名单限申诉、导出、争议三处。

### 仿真验收

在 L0 静态人口（2 万人口 / 200–600 活跃意图）上必须成立：

- 零历史用户能获得可行提案，且首次成局时间与老用户无系统性差距
- 时间约束真的会导致无解（若几乎从不无解，说明时间分布生成得太宽松）
- 稀缺角色确实成为瓶颈（若从不成为瓶颈，说明技能分布不是长尾）

### 现有可参考的先例

本仓库尚无代码。首批测试即是先例，需要格外注意上面"好测试"的定义，避免后续测试跟着错的样板长。

## Out of Scope

| 项 | 理由 |
|---|---|
| **A2A 外部互操作** | 架构规定 A2A 只用于跨运行时/组织/信任边界。v1 没有外部 agent，第一方走内部领域命令即可。不是砍范围，是它此时无对象 |
| **完整组织者工作台** | 机会模板、候补池、补位、改期、负责人移交、多团队公平分配、运营分析。最小发布能力已在范围内 |
| **持续共同体的完整治理** | v1 只做"候选提示"，不做共同体自己的目标、成员规则、可见范围 |
| **多校园租户** | `campus_id` 字段保留，但跨校协作、地方策略差异、租户级隔离不实现 |
| **学习排序** | 规则 + 求解起步。积累足够真实的接受/拒绝/完成信号之前不引入 ML 排序 |
| **外部工具回调**（GitHub / Figma / 日历） | 证据先靠手动上传。MCP 接入是后续增量 |
| **虚拟校园与校园地图** | 已从产品设计中移除。地点只是筛选字段 |
| **商业化** | 组织者付费、SLA、治理分析 |
| **Apache AGE / 独立向量库 / 独立图库** | 均未达采用门槛 |
| **协同编辑（Yjs）** | 共域对象用领域事务，不用 CRDT。文档协同是后续 |
| **未成年人支持** | 首期限定 18 岁以上；覆盖未成年人需独立的年龄、监护、混龄隔离设计 |

## Further Notes

### 依赖顺序

`Clock` 端口和 `is_synthetic` 必须先于任何领域代码落地。它们现在各是一行接口和一个字段；写完领域层再补就是跨几十个文件的重构。

### 三个最脆弱的地方

**稳定性检查的计算成本没验证过。** 理论正确，但"对每个成员验证不存在更好的候选组"在 200 人规模下是什么量级，容量护栏里写的 1 秒纯属估计。这是全系统唯一一个既新增、又没有成熟工程先例的环节，**压测之前不该当它已解决**。

**deadline 谎报没有对策。** 一旦"截止越近越优先"，用户就有动机谎报。对策候选是"声明后不可缩短"或"谎报的成本体现为可选组变少"，两者都未定。不能假装 deadline 是诚实上报的。

**组织者供给是冷启动单点。** 产品逻辑上"供给先行"是对的，但它意味着第一批增长完全依赖拿下几个院系或赛事方。拿不下来，学生侧的自发意图撑不起流动性，漏斗第一段就会空转。

### 仿真的边界

仿真只能**排除坏设计，不能证明好设计**。仿真人口的分布是我们自己写的，它会验证我们的假设而不会推翻它。仿真显示崩了是可信的坏消息；显示很美只说明"在我们假设的世界里很美"。**不得将仿真结果作为产品有效性结论对外表述。**

### 冻结 schema 前必须完成的研究

见 [`04-治理与安全`](../04-治理与安全.md) §9。其中影响本 PRD 的两项：个人/关系/共同体记忆分别采用什么审批门槛（影响 `MemoryFacet`），以及用户允许 agent 代为返回哪些条件响应（影响 `DelegationGrant`）。这两项应在实现记忆与协商模块之前有结论。

### 产品名

"共域 / CoField" 是内部代号。对外名字需要做用户测试，在此之前界面留占位。
