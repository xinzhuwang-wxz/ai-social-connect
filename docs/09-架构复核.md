## 1. 用户是由什么表达的

> 「一方面可以写一些介绍，另一方面是由这些事件以及完成这些事件过程中的
> 记忆来表达的」

| 要素 | 落点 | 状态 |
|---|---|---|
| 自己写的介绍 | `principals.self_intro` | ✅ 进语义索引，可逐项授权与撤回 |
| 完成过的事件 | `shared_events` + `event_members` | ✅ 「我参加过的」那一屏 |
| 过程中的记忆 | `memory_facets`（派生自 `evidence`） | ✅ 本人逐项确认，随时可撤销 |

**这三样正是下一次成局证明能引用的全部。** 闭环判据实测：同一条需求，
有已确认切面时的证明比没有时多恰好三行，一行不多一行不少。

## 2. 智能体到底有几个（这一条被反复问，所以写死）

口述里的「每个用户有一个智能体」在功能上是三件事，拆开之后答案很清楚：

| 它要替我做的事 | 现在由谁做 | 形态 |
|---|---|---|
| 帮我把需求说清楚 | 抽取器 + 最多两个追问 | ✅ 有，但不是一个"对象" |
| 替我盯着有没有合适的 | 窗口清算 → 提案 → 邀请提醒 | ✅ 有，形态是推送不是轮询 |
| 替我做决定 | **刻意不做** | 🚫 红线 |

所以**没有缺失的智能体，只有缺失的叙事**。三件事里两件已经在跑，
第三件是不可越过的约束。

### 为什么不做成"每人一个 agent 对象"

不是实现难度，是三条判断：

1. **两万人两两 agent 协商 = 2 亿次对话**，而每次对话都是一次披露事件。
   全局视角的活交给求解器，需要授权的活才交给人
2. **首提案偏差**（Magentic Marketplace 实测）：agent 市场里响应速度相对
   质量的优势达 10–30 倍。赢的是回得快的 agent，不是最合适的人
3. 自由格式 agent 对话是提示注入的攻击面

### 唯一人格化的 agent 属于「事」

场域智能体（#11）绑一个共域，拿能力令牌，令牌绑空间 + 用途 + 策略纪元。
它读不到任何人的私有记忆，也读不到别的共域——不是因为没写那段查询，
是因为它手上只有这一个空间的画布。

**N+1 里的那个 +1 就是它。**

## 3. 需求发布的 SOP

> 「我的智能体跟我对清楚需求，然后发布一个比较结构化的内容」
> 「但它也不能一直反问你」

```
一句话  →  抽取器  →  结构化卡（每个猜的字段带「我猜的」）
       →  用户过目改正  →  确认  →  进池子
```

- 追问上限**两个问题**（`FollowUpQuestion`），不会一直反问
- 抽不准的字段标 `uncertain`，**绝不猜**
- `raw_expression` 全文保留——结构化装不下的那半句留给语义召回

结构化的形状（`IntentContent`）：目标 / 我能出 / 我缺 / 时间 / 地点 /
人数 / 我的底线 / 还没定的事。**这就是发布到平台上、agent 好读的那份东西。**

## 4. 初筛不能太个性化

> 「结构化需求里的限制条件是比较 general 的，具体的个性化内容到时候才聊」

现在**正是这样**，而且分层是显式的：

```
general 硬约束     →  SQL 精确过滤（缺的角色有人能补、校区）
装不进字段的       →  语义召回（bge-m3，实测 6.4 倍富集）
说不清楚的         →  抽取器追问，最多两个
不该被自动判的     →  留给真人
```

硬约束只剩两条，时间刚被降级（ADR 0006）。个性化的部分**全部**走语义那一路——
「想找个写朋克风格文案的」里的"朋克"没有任何字段装得下，而实测 top-20
里 45% 命中（基线 7.0%）。

**顺序不能反**：先按 general 过滤，再在幸存者里做语义比较。反过来会有
侧信道泄露，而且高选择性下 post-filter 的召回会崩。

## 5. 组队之后的群聊 —— 已建成

> 「组完以后大家被拉到一个聊天框里，类似 N+1 的形式」
> 「智能体发一些话题卡引导大家聊，目的是促成尽快达成一致」

已建成（`space_messages` + `space/chat` + 三个端点 + 16 个用例）。

建的时候排除了两个错误选项：

- ❌ **塞进 `space_items`** —— 条目有状态、有负责人、有截止时刻、进不进度；
  消息一样都没有。混在一起，"做完了多少"会被聊天量冲淡，而不变量 6 说的
  正是**空间因真实行动证据生长，不因聊天量生长**
- ❌ **复用 `negotiation_messages`** —— 那七种受限类型是**成局前**的，
  每一句都是披露事件所以必须受限。成局后的人已经在同一个组里，
  **约束的理由消失了，约束就该消失**

`space_messages`：`said`（一句话）/ `topic`（一张话题卡），话题下挂**一层**
回复——两层以上的嵌套在手机上没人读得下去，而读不下去的讨论等于没发生。

聊天记录**不分页不截断**：「大家也可以看到整体的聊天记录」是这一层的承诺，
一个默认只给最近五十条的接口会让"看看当时怎么说的"变成做不到的事。

### 话题卡不是闲聊

助手发的 `topic` **只能来自还没定的事**——开着的决策门、成局证明里
留给真人的那几条。它把"该聊的"变成一句可以回答的话，不是活跃气氛。
凭空造话题的助手会很快被所有人忽略，之后它说什么都没人看。

`about_item_id` 是这条的机制：**指不回去的话题发不出来**（真人发的不要求——
人想聊什么就聊什么，那不该由系统判断）。

助手也**不问第二遍**：同一件事问两次说明它没在听，而一旦被认为没在听，
它后面说什么都没人看，包括真正要紧的那几句。

### 聊天里达成的一致不算数

有人在群里说"就周四吧"，其他人回"行"，决策门**不会因此关上**——还是得
有人去点头。有一条用例专门钉住这件事。

这和"AI 起草，人类决定"是同一条：聊天是**表达**，点头是**承诺**。
两者混起来，"谁同意了什么"就没有可查的答案，而那正是这个产品最不该丢的。

## 6. 反馈与存储

> 「最后组队成功后每个人有一些反馈」「事件存进用户的事件完成表」

| 要素 | 落点 | 状态 |
|---|---|---|
| 留下的东西（返图/记录/成果） | `evidence` | ✅ 只存事实不存评价 |
| 这次做成了什么 | `Recap`（**不入库**，是证据的转写） | ✅ |
| 我的事件完成表 | `GET /me/events` | ✅ 带一起做这件事的人 |
| 点进去看跟谁经历了什么 | `/me` + `/events/{id}/echo` | ✅ |

**「反馈」这个词要拆开看**：如果指"这次留下了什么"，已建；如果指
**给队友打分**，那是刻意不做的——`evidence` 里没有任何字段能放"谁表现好"，
表里也没有。一旦有了它就变成打分系统，而打分系统会让人不敢参加
自己不擅长的事。

## 7. 我想被找到 ——【唯一的真缺口】

口述里那句「我的智能体隔段时间搜索，发现合适的需求拉过来让我确认」，
拆到最后剩下一件当前确实没有的事：

**我没有一个常驻的「我想参与这类事」的表达。**

现在被找到的途径只有两条：`skills` 字段，和 `self_intro`。前者是
"我会什么"，后者是"我是什么风格"——都不是**"我最近想干什么"**。

一个刚做完一件事、想再接一个的人，现在只能自己发一条需求。而他要的
不是发起，是**参与**。

这个缺口小但真实，它正是那句口述在功能上剩下的部分。
